# 毕设论文与答辩升级说明

本文档用于把当前项目包装成“本科校优”级别的论文与答辩材料。项目定位统一表述为：

**面向新能源汽车维修诊断的多模态可追溯混合检索增强生成系统。**

## 1. 论文主线

问题背景：

- 新能源汽车维修知识分散在维修手册、故障案例、数据流表格、仪表截图和诊断仪记录中。
- 高压电池、快慢充、HVIL、OBC、DC/DC、VCU、CAN 等系统强耦合，普通关键词检索难以给出完整排查链路。
- 直接使用通用大模型容易出现引用缺失、标准值编造和高压安全风险。

系统方案：

- 管理端上传维修资料，系统自动解析、OCR、切片、元数据抽取、embedding 和 pgvector 入库。
- 技师端支持文本问题和故障图片输入，系统融合历史上下文、图片理解结果和当前问题生成检索 query。
- 检索采用 dense vector、领域关键词补召回、rerank 精排的混合链路。
- 回答固定输出“可能原因、检查步骤、安全提醒、维修建议、引用来源、置信提示”，并展示引用证据链。

## 2. 四个创新点

1. **多模态故障输入**：支持自然语言故障现象、故障码、仪表/诊断仪图片共同进入诊断流程。
2. **领域元数据增强**：从 chunk 中提取页码、章节、系统、DTC、车型和关键词，提升引用定位和答辩可解释性。
3. **混合检索与重排序**：对比无 RAG、dense only、dense + keyword、dense + rerank、hybrid + rerank，证明系统设计必要性。
4. **带安全约束的结构化生成**：通过固定回答模板、禁止编造引用、资料不足提示和高压安全提醒降低维修风险。

## 3. 实验设计

评测脚本：

```bash
cd apps/api
python evaluate_retrieval.py --variant all --limit 6 \
  --out retrieval_eval_results.csv \
  --summary-out retrieval_eval_summary.json
```

检索消融变体：

| 变体 | 含义 | 论文用途 |
| --- | --- | --- |
| `no_rag` | 不检索知识库 | 对照直接大模型/无证据回答 |
| `dense_only` | 仅向量召回 | 验证语义检索基础能力 |
| `dense_keyword` | 向量召回 + 关键词补召回 | 验证 DTC、系统名、标准值等精确术语贡献 |
| `dense_rerank` | 向量召回 + rerank | 验证精排模型贡献 |
| `hybrid_rerank` | 向量召回 + 关键词补召回 + rerank | 作为最终系统方案 |

核心指标：

- `Hit@1/3/5`：前 K 条是否出现相关证据。
- `MRR`：第一个相关证据的倒数排名。
- `nDCG@5`：前 5 条证据的排序质量。
- `citation_accuracy_at_k`：返回引用中相关证据占比。
- `keyword_coverage_at_k`：期望故障词、系统词、标准值在证据中的覆盖率。
- `safety_evidence_coverage`：安全类问题中，高压、断电、绝缘、禁止等安全证据覆盖率。
- `avg_latency_ms`：检索链路平均耗时。

评测集说明：

- 当前 `evaluation_cases.json` 已扩展到 64 条。
- 覆盖类型包括故障码、症状描述、安全操作、图片/OCR、跨系统复合故障和维修案例。
- 论文中应说明这些样本来自模拟维修手册和典型售后场景抽象，用于系统验证，不宣称来自真实厂商数据。

## 4. 回答质量人工评分表

建议抽样 30 条问题进行人工评分，每条 0/1 标注：

| 字段 | 判定标准 |
| --- | --- |
| `answer_correct` | 答案是否覆盖主要根因和关键排查步骤 |
| `citation_match` | 引用片段是否真实支持答案 |
| `safety_compliant` | 是否包含必要高压安全提醒，且没有危险建议 |
| `no_hallucination` | 是否避免编造未出现在资料中的标准值、部件或结论 |
| `actionable_steps` | 是否给出可执行检测动作、工具或标准值 |

推荐抽样组合：

- 8 条故障码问题：P1A0C、P1A10、P1A11、BMS 绝缘、CAN、DC/DC、MCU、HVIL。
- 8 条症状问题：无法快充、READY 不上电、SOC 不上升、限扭、低压报警、仪表提示、涉水、事故后离线。
- 6 条安全问题：高压断电、绝缘测量、涉水车、事故车、HVIL 短接风险、冷却液泄漏。
- 4 条图片/OCR 问题：仪表提示、诊断仪照片、故障灯、图片中 DTC。
- 4 条多轮追问：已排除某条件后询问下一步。

## 5. 答辩演示脚本

推荐 7 分钟演示顺序：

1. **痛点开场**：展示“车辆无法快充，仪表提示充电系统故障”这类问题需要跨 BMS、快充口、HVIL、VCU 和充电桩阶段排查。
2. **知识库入库**：管理员上传维修手册，展示 pending/processing/ready 状态，说明 OCR、切片、embedding 和 pgvector 入库。
3. **文本诊断**：技师提问 `P1A0C 快充互锁异常怎么排查？`，展示结构化回答。
4. **证据链**：讲解检索关键词、召回方式、向量分数、rerank 分数、页码/章节/系统/故障码，证明答案可追溯。
5. **多模态输入**：上传仪表或诊断仪图片，展示图片理解结果参与检索。
6. **多轮追问**：追问“已确认快充口无进水，下一步测哪里？”，展示历史上下文能力。
7. **实验收束**：展示 `retrieval_eval_summary.json` 的消融结果，说明最终方案优于无 RAG 和单一路径检索。

答辩话术重点：

- 不说“系统能替代维修技师”，而说“辅助技师快速定位资料、生成可追溯排查建议”。
- 不说“完全真实原厂数据”，而说“使用模拟原厂维修手册风格数据验证系统流程”。
- 不说“模型一定正确”，而强调“引用来源、置信提示和安全提醒降低不可控风险”。

## 6. PPT 页面建议

1. 题目页：系统名称 + 技术关键词。
2. 背景与痛点：知识碎片化、高压安全、跨系统诊断。
3. 总体架构：Next.js、FastAPI、PostgreSQL + pgvector、MinIO、Redis、OpenAI-compatible、本地 embedding/rerank。
4. 知识入库流程：上传、解析、OCR、chunk、metadata、embedding、索引。
5. 问答流程：文本/图片输入、query 构造、混合检索、rerank、结构化生成、引用展示。
6. 数据库设计：users、documents、chunks、chat_messages、retrieval_hits。
7. 核心算法：dense、keyword、rerank 的消融设计。
8. 实验结果：Hit@K、MRR、nDCG、引用准确率、安全覆盖率、延迟。
9. 系统演示截图：知识库、诊断工作台、证据链、模型配置。
10. 总结与展望：接入真实诊断仪数据、工单闭环、更多车型知识库。

## 7. 验收清单

- Docker Compose 可启动 Web、API、worker、Postgres、Redis、MinIO。
- 管理员能上传资料并看到 ready/failed 状态。
- 技师能完成文本问答、图片问答、历史会话回放。
- 聊天页能展示证据链、引用、分数、关键词和 metadata。
- `evaluation_cases.json` 至少 50 条，本项目当前为 64 条。
- `evaluate_retrieval.py` 能输出 CSV 和 summary JSON。
- 论文中明确数据性质为模拟维修资料，不冒充真实厂商数据。
