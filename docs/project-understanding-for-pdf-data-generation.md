# NEV Fault QA Redesign 项目理解文档

本文档用于交给豆包理解当前项目，再由豆包生成一份高质量提示词，指导 Claude 生成适合本项目入库、检索、问答和引用的新能源汽车维修 PDF 数据。

## 1. 项目定位

`nev-fault-qa-redesign` 是一个新能源汽车多模态 RAG 维修问答系统。目标用户是维修技师和管理员。系统支持管理员上传维修资料，后台自动解析、切片、向量化并写入知识库；技师在诊断工作台输入故障现象、故障码、车辆状态，或上传仪表/零部件图片，系统检索知识库后生成可执行的诊断建议，并展示引用来源。

核心使用场景：

- 管理员上传维修手册、故障案例、表格、图片等资料。
- 系统把资料转成 `chunks`，写入 PostgreSQL + pgvector。
- 技师提问，例如“车辆无法快充，仪表提示充电系统故障，应该如何排查？”
- 系统按语义向量检索知识片段，再用 rerank 精排。
- 大模型依据检索片段输出固定结构答案：可能原因、检查步骤、安全提醒、维修建议、引用来源、置信提示。

## 2. 技术架构

主要组件：

- Web：Next.js + TypeScript + Tailwind CSS。
- API：FastAPI。
- 数据库：PostgreSQL + pgvector。
- 队列/缓存：Redis。
- 文件存储：MinIO，失败时降级保存到本地 `uploads/`。
- 模型接口：OpenAI-compatible chat/vision API。
- 本地模型：`BAAI/bge-m3` 做 embedding，`BAAI/bge-reranker-v2-m3` 做 rerank。

当前 Docker 启动方式：

```bash
docker-compose -f docker-compose.yml -f docker-compose.cn.yml up -d --build
```

访问地址：

- Web: `http://localhost:3001`
- Chat: `http://localhost:3001/chat`
- API docs: `http://localhost:8000/docs`
- MinIO console: `http://localhost:9001`

默认账号：

- 管理员：`admin@example.com` / `Admin123!`
- 技师：`tech@example.com` / `Tech123!`

## 3. 知识库入库流程

管理员在“知识库管理”页面上传资料。上传字段包括：

- `knowledge_base_id`：知识库 ID。
- `title`：资料标题。
- `file`：文件本体。

支持格式：

- PDF
- Word `.docx`
- Markdown / TXT
- CSV
- Excel `.xlsx`
- 图片 `.png/.jpg/.jpeg/.webp/.bmp`

后端流程：

1. 文件保存到 MinIO；如果 MinIO 不可用，降级保存到本地 `uploads/`。
2. 创建 `documents` 记录，状态默认为 `pending`。
3. 创建 `ingestion_jobs` 记录。
4. worker 每 5 秒轮询 `pending` 或 `failed` 的任务。
5. 解析文件文本。
6. 对 PDF 中没有可提取文本的空白页调用视觉 OCR。
7. 对解析文本切片。
8. 调用本地 embedding 模型生成向量。
9. 写入 `chunks` 表。
10. 文档状态更新为 `ready`；失败则为 `failed` 并记录错误。

## 4. PDF 解析与切片细节

PDF 使用 `pypdf.PdfReader` 的 `page.extract_text()` 提取文本。每页文本被拼接成一个大文本字符串。

如果某些 PDF 页提取不到文字，系统会用 PyMuPDF 把该页渲染为图片，再调用视觉模型 OCR。OCR 提示会要求保留维修资料、仪表盘、故障码截图、线路图中的关键标签、故障码、零部件名称和表格内容。

切片逻辑：

- 默认每片约 `900` 字符。
- 相邻片段重叠 `120` 字符。
- 空行会被清理。
- 每个 chunk 的 metadata 只包含：
  - `title`
  - `filename`
  - `chunk_index`

重要限制：

- 当前系统不保存 PDF 页码到 chunk metadata。
- 当前系统不解析 PDF 的章节层级、表格结构或图片坐标。
- 引用展示主要显示资料标题、文件名、片段内容和分数。
- 因此，生成 PDF 时应把“页码、章节号、车型、系统、故障码、表格标题”等关键信息直接写进正文，让它们进入 chunk 内容。

## 5. 检索与回答机制

问答流程：

1. 用户在 Chat 页面选择知识库。
2. 用户输入文本问题，可选上传图片。
3. 如果上传图片，系统先调用视觉模型生成图片描述。
4. 系统把最近历史问题、当前问题、图片描述拼成检索 query。
5. 使用本地 `BAAI/bge-m3` 生成 query embedding。
6. 在 `chunks` 表中按 pgvector 余弦相似度取候选片段，候选数量约为最终数量的 4 倍，至少 12 个。
7. 使用 `BAAI/bge-reranker-v2-m3` 对候选片段精排。
8. 默认返回前 6 个片段给大模型。
9. 大模型按固定结构输出维修诊断答案。
10. 系统保存回答和引用片段到 `retrieval_hits`。

系统提示词要求答案固定结构：

```text
1. 可能原因
2. 检查步骤
3. 安全提醒
4. 维修建议
5. 引用来源
6. 置信提示
```

系统禁止编造引用。资料不足时，应明确说明需要补充检测数据。

## 6. 什么样的 PDF 数据最适合本项目

本项目需要的不是普通说明书，而是能支撑维修诊断问答的“高密度、可检索、可引用”的维修知识资料。PDF 内容应尽量贴近真实新能源汽车售后维修手册、故障诊断手册、案例库和检测工单。

高质量 PDF 应满足：

- 文本可复制、可被 `pypdf` 提取，不应只依赖扫描图。
- 单栏排版优先，避免复杂双栏导致文本顺序错乱。
- 每页开头显式写出页码、章节、车型、系统名称。
- 每个故障码都要和故障现象、触发条件、可能原因、检测步骤、标准值、维修建议绑定。
- 每个表格都应有标题，并在单元格中使用清晰文字，避免只有图片化表格。
- 每个诊断流程都应有明确编号，方便 chunk 内保留顺序。
- 关键术语要重复出现在相关段落，例如 BMS、OBC、DC/DC、VCU、MCU、绝缘监测、预充、快充互锁、CAN 通讯。
- 每个章节应能独立回答一个或多个维修问题，避免大量跨页引用才能理解。

## 7. 推荐 PDF 数据集内容结构

建议让 Claude 生成一组 PDF，而不是一个超长 PDF。每份 PDF 对应一个维修知识主题，便于上传、管理和引用。

推荐生成 10 到 15 份 PDF：

1. 高压电池系统维修诊断手册
2. BMS 故障码与数据流诊断手册
3. 快充/慢充系统故障诊断手册
4. OBC 与 DC/DC 转换器维修手册
5. 驱动电机与电机控制器 MCU 诊断手册
6. 高压互锁 HVIL 与绝缘故障排查手册
7. 热管理系统故障诊断手册
8. 整车控制器 VCU 与 CAN 通讯故障手册
9. 仪表报警与用户故障现象对照手册
10. 新能源汽车典型维修案例库
11. 低压供电与唤醒故障诊断手册
12. 事故车/涉水车高压安全检查手册

每份 PDF 建议包含：

- 封面：资料名称、适用车型、版本号、发布日期、适用范围。
- 目录：章节编号和标题。
- 安全说明：高压断电、PPE、等待放电、绝缘工具。
- 系统概述：部件位置、功能、信号流、控制逻辑。
- 故障码表：DTC、含义、触发条件、冻结帧关注项、可能原因。
- 诊断流程：步骤编号、操作、工具、标准值、异常分支。
- 数据流标准值：项目、正常范围、异常含义。
- 连接器/端子表：端子号、线色、信号名、正常电压/电阻。
- 维修案例：客户抱怨、车辆信息、故障现象、诊断过程、根因、维修结果。
- 复核与交付：清码、路试、充电验证、客户告知。

## 9. 单个故障条目的推荐写法

每个故障码或故障现象建议使用如下结构。这样最容易被 chunk 保留，并能支持问答引用。

```text
章节 4.2 / 页码 12 / 系统：快充系统 / 车型：NEV-A01
故障码：P1A0C
故障名称：直流快充互锁回路异常
用户现象：插入快充枪后仪表提示“充电系统故障”，充电桩显示握手失败。
触发条件：VCU 检测到快充枪连接信号有效，但 HVIL 回路电压低于 2.5V 持续 500ms。
可能原因：
1. 快充口微动开关接触不良。
2. 快充线束 HVIL 回路断路或端子退针。
3. BMS 或 VCU 对互锁信号采样异常。
4. 快充座进水导致信号短路。
检查步骤：
1. 断开高压维修开关，等待 5 分钟，确认高压母线电压低于 30V。
2. 检查快充口外观、锁止机构和进水痕迹。
3. 测量 X21-3 至 X21-4 之间电阻，正常应小于 1Ω。
4. 使用诊断仪读取 VCU 数据流“快充互锁状态”，正常应为 Closed。
5. 摇动快充口线束并观察互锁状态是否跳变。
标准值：
- HVIL 回路闭合电阻：小于 1Ω。
- VCU 互锁输入电压：4.5V 到 5.2V。
维修建议：若端子退针，修复端子并重新锁止；若快充口进水，替换快充座总成。
复核方法：清除故障码，执行快充握手测试 3 次，确认无故障复现。
安全提醒：禁止在高压未下电时拔插快充座高压连接器。
```

## 10. PDF 生成时必须避免的问题

不要生成以下类型的数据：

- 只有泛泛介绍，没有故障码、标准值和检测步骤。
- 大量营销文案、产品宣传语、历史背景。
- 缺少车型、系统、页码、章节号。
- 同一故障只写“检查线路或更换模块”，没有可执行测量步骤。
- 表格没有标题，或表格内容过度依赖视觉布局。
- 只有图片，没有可提取文本。
- 两栏/三栏复杂排版导致文本抽取顺序混乱。
- 同一术语多种写法混用但不解释，例如同时使用 OBC、车载充电机、充电模块却不说明等价关系。
- 编造危险操作，例如带电拔插高压连接器。
- 给出不符合高压安全规范的维修建议。

## 11. 推荐覆盖的故障现象与问法

PDF 数据应能支持这些用户问题：

- 车辆无法快充，仪表提示充电系统故障，如何排查？
- P1A0C 快充互锁异常可能是什么原因？
- BMS 报绝缘电阻低，下一步应该测哪里？
- 车辆 READY 不上电，但 12V 电池正常，怎么诊断？
- 充电过程中 SOC 不上升，可能是 OBC 还是 BMS 问题？
- 电机控制器过温限扭，如何区分冷却系统和传感器故障？
- CAN 通讯故障导致多个控制器离线，应如何定位？
- 涉水后高压系统报警，交车前要检查哪些项目？
- 低温环境下快充功率低，是故障还是保护策略？
- 更换 DC/DC 后仍有低压蓄电池亏电，如何排查休眠电流？

因此 PDF 中应覆盖：

- 故障码查询。
- 无故障码但有症状的诊断。
- 仪表报警语与故障系统映射。
- 数据流解释。
- 端子测量标准。
- 维修后验证。
- 安全边界。

## 12. 给豆包生成提示词时的重点

豆包需要生成给 Claude 的提示词时，应明确要求 Claude 输出“可直接用于生成 PDF 的内容”，并且内容必须服务本项目 RAG 入库。

提示词应要求 Claude：

- 扮演新能源汽车售后技术资料工程师、诊断专家和维修手册编写员。
- 生成多份结构化 PDF 资料，而不是零散问答。
- 每份资料聚焦一个系统或主题。
- 使用中文。
- 使用真实维修手册风格，但不要声称来自真实厂家。
- 包含大量故障码、症状、检测步骤、标准值和维修案例。
- 每页/每节显式写出页码、章节号、系统名和关键词。
- 保证文本可抽取，优先单栏排版。
- 生成资料时兼顾语义检索：同一条知识中要包含用户可能搜索的自然语言现象和维修术语。
- 生成资料时兼顾引用：每个片段应有清晰标题和自包含上下文。
- 避免危险或不规范操作。

## 13. 给 Claude 的输出格式建议

如果 Claude 不能直接生成 PDF 文件，建议让 Claude 输出 Markdown 或 HTML，再由后续工具转换为 PDF。Markdown/HTML 应遵循：

- 一级标题为资料名称。
- 二级标题为章节。
- 三级标题为故障码或故障场景。
- 表格使用标准 Markdown 表格或 HTML table。
- 每个分页位置插入明显标记，例如：

```text
--- 第 12 页 / 章节 4.2 / 快充系统 / 关键词：P1A0C 快充互锁 充电握手失败 ---
```

该分页标记会进入文本抽取结果，帮助 RAG 引用更可读。

## 14. PDF 质量验收标准

生成的 PDF 数据上传到本项目后，应满足：

- 文档状态变为 `ready`。
- 知识库中产生足够 chunk。
- 用故障码提问能检索到对应故障条目。
- 用自然语言现象提问也能检索到对应条目。
- 回答中引用来源能显示正确资料标题和相关片段。
- 回答能给出具体检测步骤、标准值、安全提醒和维修建议。
- 对资料未覆盖的问题，回答应能提示资料不足，而不是编造。

建议验收问题：

```text
P1A0C 快充互锁异常怎么排查？
车辆无法 READY，但 12V 电压 12.6V，仪表显示高压系统故障，先查什么？
快充时 SOC 不上升但充电桩显示已连接，可能原因有哪些？
BMS 报绝缘电阻低于 100kΩ，维修前安全步骤是什么？
电机控制器温度 95℃ 且车辆限扭，怎么判断水泵故障？
```

## 15. 总结

这个项目的 PDF 数据应以“维修诊断可执行性”为核心，而不是以“说明书完整性”为核心。最有价值的资料是包含故障现象、故障码、触发条件、可能原因、检测步骤、标准值、维修建议、复核方法和安全提醒的结构化文档。

因为当前系统的 PDF 解析主要依赖文本抽取和字符切片，生成数据时必须把页码、章节、车型、系统、故障码、关键词等信息显式写在正文里。这样才能让 embedding 检索、rerank 精排和最终引用都更稳定。
